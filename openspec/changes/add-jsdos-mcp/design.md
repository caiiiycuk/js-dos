# Design

## Context

Мотивация и область изменения описаны в `proposal.md`. Ниже приведены проверенные ограничения текущего кода.

- В `src/public/types.ts` и `src/main.tsx` публичный `DosProps` не предоставляет операции редактора. Состояние редактора хранится в `src/store/editor.ts`, а загрузка бандлов реализована в `src/player-api-load.ts`.
- В `src/window/prerun-window.tsx` изменённая конфигурация записывается в архив перед Play. В `src/frame/editor/editor-fs-frame.tsx` download и restart используют `ci.persist(false)`. Следовательно, отдельный вызов persist не гарантирует включение ещё не применённой конфигурации редактора.
- В `src/window/dos/dos-window.tsx` исходные `bundle`, `bundleChanges` и `initFs` очищаются после передачи backend. Нельзя рассчитывать на наличие исходного ZIP в store после запуска.
- `save()` из `src/player-api.ts` сохраняет changes и не заменяет экспорт полного бандла. Пакет `emulators` предоставляет `bundleUpdateConfig`, файловые операции CI, события, ввод и скриншот. Скриншот недоступен до первого кадра.
- `src/window/dos/dos-runtime.tsx` ставит эмулятор на паузу при скрытии вкладки. Звук в `src/window/dos/sound/audio-node.ts` может требовать настоящего пользовательского жеста.
- `src/main.tsx` по умолчанию загружает эмуляторы с CDN. Существующий `.github/workflows/build.yml` готовит `public/emulators` и собирает публикацию с base `/latest`. Нужен отдельный вход сборки для локальной поставки, а не использование случайного содержимого `dist/`.

В корне проекта нет общего тестового runner для API редактора. Тесты соседнего checkout `emulators` можно использовать как справочный материал, но реализация и новые проверки остаются в этом репозитории. Соседний `dosbox-x-mcp-server` управляет отладчиком и не является сервером Studio.

## Goals / Non-Goals

**Goals:**

- Использовать один экземпляр js-dos для пользователя и агента с поддерживаемым API вместо управления DOM.
- Разделить MCP, локальный браузерный канал и публикуемый проект, чтобы временная сессия не попадала в результат.
- Сохранить существующие CDN-настройки, поведение обычного плеера и API сохранения changes. Все дополнения к публичному API должны быть совместимыми.

**Non-Goals:**

- Не создавать новый редактор, движок эмуляции, desktop shell или отдельную систему отладки DOSBox-X.
- Не включать headless/CI без браузера в первую поставку. Не устанавливать и не распространять браузер вместе с MCP.
- Не обещать автоматическую проверку произвольной игры, обход ограничений звука, автономность sockdrive или восстановление всех несохранённых изменений после аварийного закрытия браузера.
- Не обновлять произвольные существующие приложения. Генератор создаёт новый проект; дальнейшие правки остаются обычной работой с его исходниками.

## Decisions

### 1. Rust stdio и обычный браузер

В `mcp/` создаётся самостоятельный Rust crate с официальным `rmcp`, Tokio и локальным HTTP/WebSocket-сервером. Точные версии фиксируются в `Cargo.lock`. HTTP-сервер запускается на случайном свободном порту `127.0.0.1`; системная команда открывает его адрес в браузере. Логи идут в stderr.

Веб-страница Studio и её канал управления обслуживаются с одного origin. Браузерный модуль вызывает только типизированные операции редактора и CI, затем возвращает структурированные ответы. Передача архивов и кадров ограничивается по размеру и не превращается в неограниченный журнал сообщений.

Tauri не выбран, потому что системные WebView добавляют различия между ОС и требования к установленному runtime. Playwright не выбран как обязательная зависимость, потому что задача требует видимую совместную Studio, а не управление произвольным браузером. Отдельный debugger MCP также не требуется для ввода, кадров и файлов CI.

### 2. Единая встроенная сборка runtime

Отдельный build entry в `mcp/` собирает локальную страницу Studio, bridge, js-dos JS/CSS и нужные ресурсы из установленного `emulators`. Сборка не использует пользовательский корневой `index.html` и не меняет CDN-сборку. Готовый набор включается в Rust-бинарь через `include_bytes!` и сгенерированный список ресурсов.

Для первой поставки поддерживаются обычные worker-варианты DOSBox и DOSBox-X. В набор включаются libzip, worker scripts, WASM, аудио и вспомогательные UI-ресурсы, нужные этим режимам. Необязательные debugger/JSPI-варианты не объявляются поддержанными без включения и проверки всех их ресурсов. Отсутствующий необходимый файл останавливает сборку, а не вызывает CDN fallback.

Локальная Studio явно получает локальный `pathPrefix` и не полагается на публичное значение по умолчанию. Один и тот же проверенный набор копируется в создаваемые проекты вместе с лицензиями и версиями. Manifest ресурсов фиксирует пути, размеры и контрольные суммы. Сжатие бинаря не является условием готовности.

Альтернатива с загрузкой `latest` при запуске отклонена, потому что нарушает автономность и делает результат зависимым от текущей публикации CDN. Встраивание браузера отклонено из-за размера и отдельного обновления безопасности.

### 3. Общий API редактора, а не доступ к Redux

В `src/public/types.ts` добавляется `DosEditorApi`, доступный через новое поле `DosProps.editor`. Он предоставляет состояние и ревизию, открытие бандла, конфигурацию, файловые операции, start/restart и полный snapshot. Внутренний store наружу не передаётся. Существующие методы `DosProps` сохраняют значения и семантику.

Общая реализация рядом с `src/player-api-load.ts` использует текущую загрузку и `emulators.bundleUpdateConfig`. UI Play, restart, download, импорт и удаление файлов переводятся на те же операции, сохраняя ошибки и подтверждения интерфейса. `save()` остаётся сохранением changes.

Создание из папки и проверка входного ZIP выполняются Rust-частью с ZIP-библиотекой и пределами распаковки. Новый бандл получает требуемые конфиги до открытия в Studio. Изменение файлов уже открытого бандла использует готовый CI; до готовности возвращается явная ошибка состояния. Пользователь или агент запускает пустой бандл перед пошаговым импортом файлов. Самостоятельный скрытый запуск ради файловой операции не выполняется.

Для корректного lifecycle требуется исправить закреплённый пакет `emulators`: `CI.exit()` и ошибка инициализации должны освобождать `AudioContext`, `AudioWorkletNode`, `MessagePort` и обработчики пользовательского жеста. Исправление готовится в отдельном checkout внутри допустимой области проекта, без изменения пользовательской работы соседнего `emulators`, и подключается как проверенная фиксированная версия зависимости, а не ручная подмена `node_modules`. До подключения исправленной зависимости lifecycle и release не считаются завершёнными. ZIP-библиотека Rust нужна для проверки входа и сборки папки, но снимки работающей DOS-файловой системы по-прежнему создаёт backend, а не копия состояния на стороне Rust.

### 4. Ревизии и согласованный snapshot

Редактор имеет очередь изменяющих операций и монотонную ревизию. UI и API увеличивают одну ревизию после принятой правки. MCP-команда передаёт `expectedRevision`; проверка выполняется при входе в общую очередь, а не только на Rust-стороне. Во время полного snapshot новые правки ожидают завершения операции. Частично выполненная пакетная запись возвращает список выполненных элементов и новую ревизию.

Ревизия относится к действиям редактора. Она не увеличивается на каждую запись работающей DOS-программы. Для snapshot работающий backend временно ставится на паузу; прежнее состояние паузы восстанавливается после упаковки или ошибки.

До запуска snapshot берёт сохранённый полный архив открытого бандла. После запуска snapshot получает `ci.persist(false)`. Затем в обоих случаях `bundleUpdateConfig` записывает текущий draft конфигурации в полный ZIP. Перезапуск загружает полученный снимок; экспорт передаёт его Rust-части. Нельзя использовать `persist(true)` или подменять отсутствующий полный архив пустыми changes.

Rust хранит исходный архив и последний подтверждённый полный snapshot текущей сессии. Закрытие вкладки не считается сохранением текущей DOS-файловой системы. При переподключении состояние перечитывается; восстановление из последнего snapshot выполняется явно с предупреждением о возможных более новых правках. Постоянная база данных и автоматическое снятие полного архива после каждой клавиши не вводятся.

Альтернатива с экспортом только `ci.persist(false)` отклонена из-за неприменённой конфигурации редактора. Независимая копия конфигурации в Rust также отклонена, поскольку разошлась бы с пользовательским UI.

### 5. Конечный набор MCP-операций и жизненный цикл

Инструменты группируются по наблюдаемым действиям. Точное разбиение имён не является публичным требованием specs, но первый набор покрывает следующие операции:

- Studio: открыть локальную страницу, получить состояние соединения и редактора, закрыть управляемый экземпляр плеера.
- Бандл: создать/открыть, прочитать/изменить конфигурацию, прочитать/изменить файлы, запустить/перезапустить, экспортировать.
- Диагностика: получить сообщения и кадр, выполнить ограниченный сценарий ввода, проверить бандл или созданный проект.
- Проект: сгенерировать выбранный preset и открыть явно включённую диагностическую preview.

Один процесс обслуживает один активный редактируемый бандл. Параллельная работа достигается отдельными MCP-процессами без общего порта или общей авторизации. Второе подключение страницы не получает право незаметно заменить активную Studio.

В конверте команды передаются идентификаторы сессии, соединения и запроса, ожидаемая ревизия и deadline. Ошибки различают неверный ввод, конфликт, отсутствие готовности, отсутствие соединения, таймаут, ошибку backend и ошибку файловой системы. При разрыве изменяющей команды её исход может быть неизвестен; автоматический повтор запрещён. Поздние ответы старого соединения отбрасываются.

### 6. Ограничения безопасности и запись на диск

Секрет сессии передаётся странице через URL fragment и предъявляется при установлении управляющего соединения. Его нельзя помещать в stdout, обычные логи или шаблоны. Проверяются Host, Origin и секрет; для явно запущенной preview разрешается только её конкретный локальный origin. Loopback сам по себе не считается авторизацией. Удалённый сетевой MCP-сервис в scope не входит.

HTTP-маршруты отдают только встроенные ресурсы и явно подготовленные данные сессии, а не произвольные пути компьютера. Локальные импорты и назначения выбираются через MCP. Архивы проверяются на абсолютные пути, traversal, ссылки, дублирующиеся конфликтные имена и превышение квот. Для больших данных применяются ограничения длины, числа файлов, распакованного объёма и времени обработки.

Полный экспорт сначала записывается во временный файл на том же файловом разделе. После успешной записи он публикуется операцией, которая не заменяет существующий файл без разрешения. Явная замена должна сохранять старый файл при неудаче; поведение проверяется отдельно на Windows. Генерация проекта использует собственную временную папку и публикует только полный результат в новое назначение. При отказе удаляются лишь временные файлы текущей операции.

Запуск проекта выполняет пользовательский локальный код даже при фиксированной команде `npm run build`. Поэтому диагностика запускает только известные команды preset после явного разрешения, без произвольной строки shell. Вывод, время работы и дочерние процессы ограничиваются. Автоматическая установка npm-зависимостей не выполняется.

### 7. Самостоятельные шаблоны

В `mcp/` хранятся проверяемые шаблоны `html`, `vite`, `react`, `vue`, `angular`. У HTML нет этапа сборки; остальные варианты получают согласованные фиксированные версии инструментов. React/Vue используют Vite, Angular использует стандартные builder и scripts Angular. Генерация не требует глобального Angular CLI или доступа к сети, поскольку создаёт исходники из шаблона.

Ресурсы размещаются в статической папке проекта, например `public/js-dos/`, а HTML получает аналогичную папку рядом со страницей. Angular настраивается копировать папку в build output. Шаблон передаёт локальные адреса CSS, JS, `pathPrefix` и бандла. Пути проверяются в dev и production; нельзя жёстко зашивать временный origin MCP.

React/Vue/Angular создают плеер после появления контейнера и вызывают `stop()` при уничтожении. Если создание или остановка завершились асинхронно после unmount, код всё равно завершает соответствующий экземпляр. Для React проверяется повторный mount в режиме разработки. Публикуемые страницы не содержат bridge Studio или его секрет.

Альтернатива с CDN отвергнута пользователем. Добавление npm-зависимости `js-dos` поверх скопированного runtime не требуется, поскольку создало бы второй источник версий.

### 8. Диагностика без универсального управления браузером

Проверка бандла сначала анализирует ZIP и конфигурацию, затем при запросе запуска ожидает CI и события с deadline. Сценарий содержит только фиксированные шаги ввода и ожидания. Скриншот CI конвертируется в изображение MCP; отсутствие первого кадра возвращается отдельно. Сообщения собираются в ограниченный буфер с признаком усечения.

Для созданных проектов статическая проверка сверяет ресурсы и пути с manifest. Сборка выполняется только после отдельного разрешения и при установленных зависимостях. Preview запускает локальный сервер проекта и открывает страницу в обычном браузере. Отсутствие браузерного подключения не считается успешной проверкой.

Диагностический модуль страницы подключается до инициализации плеера только в явной preview-сессии. Он передаёт `error`, `unhandledrejection`, ошибки ресурсов и события js-dos. Для HTML модуль добавляется в ответ локального preview-сервера без изменения экспортированного файла. Для Vite/React/Vue используется отдельный dev hook, для Angular отдельная диагностическая конфигурация. Обычная сборка не содержит управляющего модуля, адреса или секрета; это проверяется по build output и сетевым запросам.

В `DosOptions` добавляется `runInBackground` со значением `false` по умолчанию. Управляемая Studio включает его явно, чтобы существующий effect не ставил плеер на паузу из-за `document.hidden`. Политики throttling и звука браузера остаются внешними ограничениями и отражаются в отчёте. Без пользовательского критерия отчёт подтверждает только наблюдавшуюся загрузку, а не корректность игры.

### 9. Проверки и releases

В `mcp/` добавляются Rust-тесты протокола, путей, квот, файловой публикации и шаблонов. Небольшой браузерный harness в этом репозитории проверяет новый API редактора на свободно распространяемом тестовом бандле с известным stdout и файлом результата. Отдельная test-only автоматизация браузера допустима, но не становится runtime-зависимостью бинаря. Runner выбирается при реализации с учётом уже установленных инструментов, без нового универсального тестового фреймворка ради нескольких проверок.

Первичная release-матрица как допущение планирования: Linux x86_64, Windows x86_64, macOS x86_64 и arm64. Все варианты встраивают одну сборку web-ресурсов. Workflow проверяет fmt, clippy, Rust-тесты, TypeScript/сборку js-dos и сборки шаблонов; выпускает бинарные файлы, checksums и сведения о лицензиях/исходниках. Документация OpenCode использует актуальный локальный stdio-формат, проверяемый перед публикацией.

Браузерные проверки на трёх ОС подтверждают локальный запуск, hidden-tab сценарий, export/reimport и отсутствие обязательного CDN. Размер бинаря и минимальные поддерживаемые версии ОС публикуются по результату сборки и проверок, а не оцениваются заранее.

## Risks / Trade-offs

- [Браузер ограничивает скрытую вкладку или звук] → Не менять обычные defaults, добавить opt-in режим и проверить сценарий переключения на всех целевых ОС. Таймаут и блокировка звука остаются явными результатами.
- [Полный snapshot велик и блокирует эмулятор] → Сериализовать операции, ограничивать размеры и снимать архив при явном checkpoint, экспорте или перезапуске, а не после каждого действия ввода.
- [Разрыв соединения или закрытие вкладки теряет более новые runtime-правки] → Хранить последний подтверждённый snapshot и не обещать восстановление несохранённого состояния. Не повторять неидемпотентные команды автоматически.
- [Неучтённый вспомогательный ресурс обращается к сети] → Использовать manifest и сетевую проверку без внешней сети для обоих backend и всех шаблонов.
- [Экспорт sockdrive выглядит автономным] → Возвращать предупреждения о внешних дисках и не подменять их содержимое пустыми changes.
- [Отличия файловой публикации и toolchain между ОС] → Проверить конфликт назначения и ошибку записи на каждой ОС. Документировать проверенную ОС/toolchain вместо обещания абсолютной переносимости.
- [Redistribution нарушает условия лицензий] → Включить notices, версии и доступ к соответствующим исходникам в release и создаваемый проект; проверить состав перед публикацией.

## Migration Plan

Сначала добавить совместимый API редактора и его проверки. Затем подключить локальную Studio и MCP, после чего добавить генерацию, диагностику и release pipeline. Существующая CDN-публикация и корневой пример не заменяются.

Перед release проверить полную цепочку: создание бандла, правка пользователем и агентом, конфликт ревизии, запуск, экспорт, повторный импорт, генерация каждого preset и запуск результата после остановки MCP. Проекты с установленными зависимостями проверяются без внешней сети на этапе загрузки runtime.

Для отката достаточно отключить MCP в клиенте и удалить скачанный бинарь. Пользовательские экспорты и проекты остаются обычными файлами; миграция их данных или формата `.jsdos` не требуется.
